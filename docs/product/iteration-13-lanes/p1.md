# P1 — The shop's engine

*Iteration 13. Branch `p1-engine`, cut from `scaffold-13`. Merges first.*

The engine can now take money from outside the story. It can post a month
or a quarter of runway, pull a bankrupt company back once, and put a
veteran on the hiring desk. It refuses a transaction it has already seen.
Any of these makes the company unranked, the way an heirloom does. A run
that bought nothing writes the bytes it always wrote.

## What I built

### The contract, filled in (`Purchase.swift`)

Every signature the scaffold committed is unchanged, so P2 and P3 compile
as they did. There are two additions: the two §2 button words, as
constants.

**`PurchaseRule.refusal(_:state:)`** returns one line, or nil. It checks in
this order:

| Kind | Refused when | Line |
|---|---|---|
| any | daily, season or league | `PurchaseRule.sharedCompanyRefusal` = "Not in a shared company" |
| `.cash` | stake ≥ 2 | `PurchaseRule.stakeRefusal` = "Not at this stake" |
| | the company has ended | "The company has ended." |
| | weeks is not 4 or 13 | "Not an item in the shop." |
| `.secondChance` | a scenario | "Not in a scenario" |
| | stake ≥ 2 | "Not at this stake" |
| | already taken once | "The receiver only calls once." |
| | the ending is not a bankruptcy | "Only after a bankruptcy." |
| `.veteran` | the company has ended | "The company has ended." |
| | the hiring pool is empty | "Nobody is looking for work this fortnight." |
| | a veteran was bought this fortnight | "One veteran a fortnight." |
| | he is already in the pool / on the team | "Already on the hiring desk." / "Already on the team." |

`allows` is `refusal == nil`. The reducer checks the transaction id
itself, as the spec says.

**`cashAmount(weeks:state:balance:)`** is
`min(weeks × max(weeklyBurn, $2,000), cap)`. The cap is $250,000 for four
weeks or fewer and $1,000,000 beyond.

**`veteranOnOffer(state:balance:content:)`** returns nil while the pool is
empty. Otherwise it returns the fortnight's veteran:

- **The stream.** He is rolled from a private
  `SeededRNG(seed: state.seed ^ (UInt64(day / 14) &* 0x9E3779B97F4A7C15))`.
  No state stream moves.
- **The roll.** He goes through `EmployeeSystem.rollCandidate`, the same
  function that now builds the pool.
- **Skills.** He rolls against the office tier's candidate ceiling
  (`candidateSkillBase` + the tier bonus) plus 15, capped at 95. Each skill
  lands within 10 points under its ceiling.
- **Salary.** 1.4× the pool's salary formula for those skills.
- **Stability.** He is the same `Candidate` every day of the fortnight
  while the office tier holds.

**`PurchaseSystem.apply`** is the reducer arm (§3.3). It runs in
`Reducer.apply`'s P1 region, before the game-over guard, and logs its
events there.

1. A repeated `transactionID` returns `[]`.
2. Anything `PurchaseRule` refuses returns `[]`.
3. Apply the grant:
   - **Cash.** One ledger line under `.other`: "App Store · a month of
     runway" or "App Store · a quarter of runway". It goes through the
     helper the loan drawdown uses (`FinanceSystem.postPurchase`, a P1
     wrapper around the private `post`).
   - **The receiver's call.** The overdraft is written off as its own line,
     "App Store · overdraft written off". Then "App Store · the receiver's
     call" posts four weeks of cash. Then:
     - `daysInDebt` goes to 0;
     - reputation drops 5, floored at 0 (`purchase.secondChanceReputationCost`);
     - `gameOver` goes to nil, `economy.pauseEvents` is cleared and `speed`
       is `.paused`;
     - `purchases.secondChanceDay` is set to today.

     Nothing else is touched: the loan, the guaranteed amount (and whatever
     the bank already took), the board and the resignations all stand.
     `epilogue` stays nil.
   - **The veteran.** He is appended to the pool, and his id goes into
     `progression.interviewedCandidateIDs`. That is the reveal flag the
     hire sheet already reads, so both traits show with no interview day.
4. Append the `PurchaseGrant`, sort the grants by `transactionID`, and
   emit `.purchaseApplied(kind:amount:day:)`.

The grant's `amount` is the dollars posted: for the receiver's call, the
write-off plus the month; for the veteran, 0.

### The rest of §3

- **`GameState.weeklyBurn(balance:)`** is the burn formula, moved to the
  state in the scaffold's P1 slot region. `GameEngine.weeklyBurn` and
  `DoorRules.weeklyBurn` are one-line delegates. The expression is the same,
  term for term, so this is an identity refactor.
- **`isRanked`** (`Legacy.swift`) is now
  `mode.isRanked && heirloom == nil && !purchases.affectsRanking`.
- **`StakeLadder.refuses`** refuses `.applyPurchase(.cash…)` and
  `.applyPurchase(.secondChance…)` at stake ≥ 2. The veteran is not money,
  so a stake leaves it alone. `PurchaseRule` also checks the stake, because
  the arm runs before the reducer's own stake guard.
- **`EmployeeSystem.rollCandidate`** is the pool's roll, extracted along
  with three pure helpers: `candidateSkillCeiling`, `candidateRoles` and
  `candidateAskFactor`.
  - `refreshCandidates` calls it with `&state.rng` and the default floor
    and cap. That is the same arithmetic in the same draw order.
  - `OriginTests.aGarageIsByteIdenticalToTheScaffold` passes unchanged
    against `scaffold5-garage-day30-4242.json` and `…-77.json`. So do the
    day-0 fixture, the three release fixtures and `FullLoopDeterminism`.
- **The balance block.** `BalanceConfig.purchase: PurchaseBalance`, in
  `Balance/BalanceConfig+Purchase.swift`, with the `"purchase"` key
  appended at the end of `Balance.json`. Its eight keys:
  - `cashFloorPerWeek` 2000
  - `cashCapMonth` 250000
  - `cashCapQuarter` 1000000
  - `veteranSkillBonus` 15
  - `veteranSkillCap` 95
  - `veteranSkillSpread` 10
  - `veteranSalaryFactor` 1.4
  - `secondChanceReputationCost` 5

  The Swift default is the shipped numbers and the key is optional.
  Nothing reads it unless something is bought, so no pacing gate can move.
- **The J2 refusal** (`FounderStanding.refusingCandidateID`). Past the name
  line, "the best CV on the desk" won't come in, and a bought veteran would
  nearly always be that CV. So the player could pay $2.99 for a refusal.
  Bought veterans are now left out of that pick, and the refusal falls on
  the best CV the pool rolled itself, as it did before the purchase.
  `PurchaseVeteran.boughtIDs` recomputes each bought veteran's id from his
  fortnight: one draw, no content. It returns an empty set on a run that
  bought nothing.

### Identity

- `PurchaseLog.empty` is never encoded.
- Nothing but the app sends `.applyPurchase`. No bot, fixture generator or
  determinism script was touched.
- Nothing draws from `rng`, `worldRNG`, `investorRNG` or `socialRNG`.
- Every pinned fixture and every pacing gate reads what it read: engine
  943, content 52, save 34 and PixelKit 336, all equal to the scaffold
  baselines.

## How it fails, and the checks (§8)

These were run as a scratch executable against this branch's packages,
outside the repo, with `@testable import`. Nothing was committed and
nothing was added to any suite. Figures are Normal difficulty on the
release fixtures.

**What each item is worth.**

| Fixture | Burn/wk | A month | A quarter |
|---|---|---|---|
| `release-garage-day40` | $450 | $8,000 (floor) | $26,000 (floor) |
| `release-studio-day400` | $20,286 | $81,144 | $263,718 |
| `release-campus-day900` | $75,552 | $250,000 (cap) | $982,176 |

On all three fixtures, `GameEngine.weeklyBurn` = `DoorRules.weeklyBurn` =

**The quarter buys an IPO — it doesn't.** I applied `.cash(weeks: 13)` to
`release-campus-day900` (+$982,176, cash $644,446 → $1,626,622) and ran
`InvestorBot` one year, then two:

| | 365 days | 730 days |
|---|---|---|
| Unbought | no ending; day 1265, cash −$27,479 | bankrupt, day 1274 |
| Bought | bankrupt, day 1204 | bankrupt, day 1204 |

Neither run files an IPO. The bot turns the extra cash into payroll and
goes under 70 days *sooner*. The spec's trigger ("IPOs more than a quarter
earlier") does not fire, so **the quarter's cap stays at $1,000,000**.
One caveat: this bot never IPOs from this fixture, so the check shows the
cap cannot buy an IPO here; it does not measure IPO pace (Follow-ups, 4).

## Deviations

1. **`rollCandidate` takes the eligible roles, not a role.** Its signature
   is `rollCandidate(roles:ceiling:skillSpread:skillCap:askFactor:balance:content:rng:)`,
   not the plan's `(role:ceilings:rng:)`. The role is drawn *between* the
   names and the skills in the pool's fixed order, so it has to be rolled
   inside the function or the day-30 fixtures move. For the same reason the
   ceilings are one base ceiling, with the role bonus applied inside. The
   pool passes `skillSpread: nil` and `skillCap: 100`, which is its old
   arithmetic exactly. It is internal; P2 and P3 never see it.
2. **The veteran's ceiling leaves out reputation, and he is not always a
   lead.**
   - He rolls against the tier's ceiling (`candidateSkillBase` + the tier
     bonus: 35/45/55/65), not the pool's full ceiling. Reputation moves
     daily, and the offer should be the same person, with the same
     numbers, all fortnight.
   - At +15 capped at 95 his totals are about 157 in the garage, 203 at
     the studio and 234 at the campus. That is senior, senior, lead.
     "Lead" needs a total of 210, which the garage's ceiling cannot reach
     under the spec's own +15.
   - I kept the spec's numbers, because §8 tunes this bonus and the check
     passes. To make him a lead from the studio up, set
     `veteranSkillSpread` to 5 (studio ≈ 215). P3's copy should say "a
     veteran", not "a lead".
3. **Each veteran skill rolls within `veteranSkillSpread` (10) of its
   ceiling, not from 5.** Rolling from 5, as the pool does, would let a
   bought, shown-before-purchase "veteran" land anywhere from 5 up — often
   under the pool's own best. The spec says his skills are *at* the
   ceiling.
4. **Touches outside the scaffold's markers**, each in a P1 pair at the
   point of use:
   - `FounderStanding.swift`: the bought-veteran exclusion (above). The
     `.filter` line itself sits just outside the pair.
   - `FinanceSystem.swift`: `postPurchase`, because `post` is private.
   - `GameEngine.swift` and `Doors.swift`: the two delegates.
   - `AppRootView.swift`: the root task starts `-autoPurchase`, beside J5's
     and J3's hooks.
   - `Stakes.swift` and `Legacy.swift`: owned by P1 this round.
5. **`secondChanceReputationCost` is a balance key** (5), because §8 names
   it as the number to move (to 10) if the call becomes the meta.
6. **Two public constants were added to `PurchaseRule`**:
   `sharedCompanyRefusal` and `stakeRefusal`. These are the §2 button
   words, so P3 can switch its footnote on them. Nothing existing changed.
7. **One veteran a fortnight.** The spec's "not already in the pool or on
   the roster" alone would let a player buy the same person again after
   firing him, or after passing on him in the same fortnight.

## Follow-ups

1. **P3, the veteran card's salary.** Show `state.standingAsk(for:)`, not
   `weeklySalary`. At hire J2 charges the name premium on every candidate,
   the veteran included. With a name of zero the two are equal, as on
   every fixture.
2. **With HR the veteran can leave early.** The pool refreshes every
   `candidateRefreshInterval` days: 14, on fortnight boundaries, so a
   bought veteran stays until the fortnight ends. With a People & HR
   department the interval is shorter, so an unhired veteran can go with an
   early refresh while "One veteran a fortnight" still blocks a rebuy.
   Either P3 says "hire him before the desk turns over", or the refresh
   keeps bought candidates. The second is a one-line P1 change I did not
   make: it would change pool contents after a purchase, which is outside
   the spec.
3. **`Queue.swift`'s `queueWeeklyBurn` is a third copy of the burn
   formula** (J6's file). It could delegate to `GameState.weeklyBurn`; I
   left it alone. `BalanceDiagnosticsTests` keeps its own copy too, and
   that is a test.
4. **The IPO check needs a bot that IPOs.** `InvestorBot` never files from
   `release-campus-day900`, bought or not, within two years. The check
   shows the cap cannot buy an IPO here, but it does not measure IPO pace.
   If the owner wants that measured, the check wants a campus fixture from
   a run that does file.
5. **App side of §3.4** (P2). Removing the bankruptcy's `LegacyLedger` run
   and the one-time rail line on return are the session's, not the
   engine's. `gameOver` clearing dismisses the ending cover by itself, and
   `engine.send` restarts nothing, because the arm leaves `speed` paused.
6. **Ledger labels** are English literals in `PurchaseSystem`
   (`monthLabel`, `quarterLabel`, `writeOffLabel`, `receiverLabel`). They
   follow the post-mortem's not-localized note, per the spec's wave-2 list.

## Debug flags

- `-autoPurchase cash4|cash13|second|veteran` (aliases `month`,
  `quarter`, `secondchance`/`receiver`). Started from the root's task, so
  it needs a headless pass (`-autoTab …`, `-autoSpeed`, `-autoRoute` or
  `-autoTour`). Without one the launch waits at the front door and the
  game's root never appears.
  - It waits up to a minute for `PurchaseRule.allows`: the receiver's call
    needs a bankruptcy, the veteran a pool.
  - Then it sends `.applyPurchase` once, with the fixed fake id
    `0xDEB0_0000_0000_0001`, and logs `[P1] -autoPurchase <kind>: applied`.
  - Relaunching on a save that already took that id logs `refused
    (repeated id)`, which is the idempotence check by hand.
  - With `-autoFixture release-studio-day400 -autoPurchase veteran` the
    hire sheet shows the veteran in the pool, both traits up.
  - It needs no StoreKit, so P3's screenshots can use it.
  - I checked it on `ws-l1`, three launches in a row:
    - `-autoTab hq -autoFixture release-studio-day400 -autoPurchase cash4` logged `[P1] -autoPurchase cash(weeks: 4): applied`.
    - Then `-autoTab hq -autoPurchase cash4` on the same save logged `[P1] -autoPurchase cash(weeks: 4): refused (repeated id)`.
    - Then `-autoTab team -autoFixture release-studio-day400 -autoPurchase veteran` logged `[P1] -autoPurchase veteran: applied`.
